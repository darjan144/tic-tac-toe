Architecture knowledge established in prep sessions**## **2.1 MVP pattern - the candidate understands this well**The candidate understands Model-View-Presenter as the primary pattern for Unity UI architecture. Key points established:- View is passive - displays only, no logic, no direct references to services- Presenter mediates between Model and View - the only layer that calls both- Model/Repository owns data - answers questions, executes commands, fires no UI events- Services (SaveManager, AudioManager, GameFlowManager) sit below the Presenter - they do not know about Presenters or Views- Dependencies point downward only: View → Presenter → Services/Repository// Correct dependency directionView holds ref to → Presenter (via \[SerializeField\] or interface)Presenter holds ref to → Repository, ServicesRepository holds ref to → nothing above itServices hold ref to → nothing above them// WRONG - what the Tic-Tac-Toe codebase currently doesView (GameResultPopup) → GameFlowManager directly // couplingView (SettingsPopup) → SaveManager, AudioManager // couplingAudioManager → SaveManager // service-to-service coupling## **2.2 MVP vs MVC - candidate can distinguish these**In MVP: Presenter pushes data to the View. View is completely passive.In MVC: View observes the Model directly and pulls data. Controller handles input and updates Model.MVP is preferred in Unity because MonoBehaviour Views are hard to make reactive without coupling them to data models. MVP keeps the View ignorant of everything except its Presenter interface.## **2.3 Event / Observer pattern - correctly understood**The candidate understands C# events (Action, Func, EventHandler) and when to use them. Key rule established: subscribe in OnEnable, unsubscribe in OnDisable - not Awake/Start/OnDestroy - because OnDisable fires even when the object is disabled without being destroyed, preventing dangling subscriptions.// Correct subscription lifecyclevoid OnEnable() => \_presenter.OnLevelConfirmed += HandleLevelConfirmed;void OnDisable() => \_presenter.OnLevelConfirmed -= HandleLevelConfirmed;## **2.4 Other patterns covered**- Object Pool - Unity ObjectPool&lt;T&gt;, for repeated spawn/destroy cycles. NOT needed for 120 static level buttons, IS needed for projectiles, particles, enemies.- Command pattern - Execute() + Undo() + history stack. Directly relevant to puzzle games with undo mechanics (NoNo Crossing).- State machine - IState interface with Enter/Tick/Exit. For AI, character controllers, UI screen flow.- Flyweight via ScriptableObjects - shared immutable data (EnemyDataSO, ShopItemSO) referenced by many instances. Not copied per-instance.- Service Locator - global registry for shared services. Use over Singleton when you need swappable implementations or testability.- Singleton - acceptable for truly global services (AudioManager, GameFlowManager) at small-to-medium project scale. The smell is not using Singleton - it is Views or Services directly calling Singletons they should not know about.# **3\. A candidate who misses this has a fundamental gap.// Correct order - NEVER grant before confirmingStep 1: Write pendingTx to disk (before anything else)Step 2: Initiate purchase with storeStep 3: OnPurchaseSuccess → AddGems() → SetRewardGranted(true) → Save()Step 4: ConfirmPendingPurchase() to storeStep 5: ClearPendingTransaction() → Save()// On every app launch:if (pendingTx != null && pendingTx.rewardGranted == false)// Crashed before grant - grant now, then confirmif (pendingTx != null && pendingTx.rewardGranted == true)// Crashed after grant but before confirm - just confirm, skip grantif (pendingTx == null)// Nothing in flight, proceed normally**Why rewardGranted matters**_Unity IAP re-delivers unconfirmed purchases on every launch (at-least-once delivery). Without the rewardGranted flag, a player who closes the app after receiving Gems but before confirming to the store would receive Gems again on next launch.
